# RCA: Day 17 Alembic Schema Drift & Metadata Namespace Pollution

- **Trigger**: `test_schema_drift_detection_reports_zero_differences` failed with `Detected unexpected schema drifts: [('add_table', Table('day15_sample_test_entities'))]`, and SQLite batch alter downgrade encountered `no such index` when dropping tables with auto-generated individual index drop statements.

---

## 1. Incident 1: Metadata Namespace Pollution via Test Entity Subclassing

### Faulty Code / Pattern
```python
# tests/test_database_async_setup.py
from app.core.database import Base  # Production DeclarativeBase

class SampleTestEntity(Base):  # POLLUTION!
    __tablename__ = "day15_sample_test_entities"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column()
```

### Root Cause
In SQLAlchemy, `DeclarativeBase` maintains an internal, mutable, singleton `MetaData` registry (`Base.metadata`). Any class inheriting from `Base` anywhere in the Python process automatically registers its `Table` in that singleton `Base.metadata`.
When `tests/test_database_async_setup.py` executed, it registered `day15_sample_test_entities` into `Base.metadata`.
Later, when `tests/test_alembic_migrations.py` executed `compare_metadata(migration_context, Base.metadata)` to verify that the database had zero schema drift against production models, Alembic inspected `Base.metadata`, found `day15_sample_test_entities`, and correctly flagged it as a missing database table (`add_table`).

### Resolution
Never inherit from production `Base` inside test files for throwaway, mock, or sandbox models. Instead, instantiate an isolated `TestBase` with its own detached `MetaData` registry:
```python
# tests/test_database_async_setup.py
class Day15TestBase(AsyncAttrs, DeclarativeBase):
    """Isolated test declarative base to prevent test models from polluting production Base.metadata."""
    pass

class SampleTestEntity(Day15TestBase):
    __tablename__ = "day15_sample_test_entities"
    ...
```
Now, production `Base.metadata` contains strictly the application's domain models (`UserModel`), and `compare_metadata` cleanly validates zero schema drift.

## 2. Incident 2: Redundant Index Drop in SQLite Batch Migration Downgrade

### Faulty Code / Pattern
```python
# alembic/versions/e25bf437c78f_create_users_table.py
def downgrade() -> None:
    # Autogenerated batch alter drops indexes before dropping table
    with op.batch_alter_table('users', schema=None) as batch_op:
        batch_op.drop_index(batch_op.f('ix_users_username'))
        batch_op.drop_index(batch_op.f('ix_users_email'))

    op.drop_table('users')
```

### Root Cause
In SQLite, `batch_alter_table` executes table recreation under the hood (`CREATE _alembic_tmp_users ... DROP users ... RENAME`). When dropping multiple indexes within `batch_alter_table`, intermediate table recreation can cause subsequent index lookups to fail with `sqlite3.OperationalError: no such index`.
Furthermore, in relational database engines (PostgreSQL, MySQL, SQLite), issuing `DROP TABLE users` automatically and atomically removes all associated constraints and indexes on that table.

### Resolution
In the initial table creation migration downgrade, simplify `downgrade()` to `op.drop_table('users')`:
```python
def downgrade() -> None:
    """Downgrade schema."""
    op.drop_table('users')
```
This guarantees atomic, deterministic rollback across all database dialects without orphan index errors.

## Permanent Prevention Rules Added to SKILL.md
1. **Isolated Test Declarative Bases**: Never subclass the application's production `Base(AsyncAttrs, DeclarativeBase)` for test-only or scratch entities. Always create a dedicated `TestBase(AsyncAttrs, DeclarativeBase)` in test suites to prevent `Base.metadata` namespace pollution.
2. **Atomic Table Dropping in Downgrades**: When rolling back an initial table creation, rely on `op.drop_table(table_name)` directly to cleanly cascade and drop all indexes without triggering SQLite batch alter recreation errors.
3. **Automated Schema Drift Verification**: Continuously assert `compare_metadata(migration_context, Base.metadata) == []` in CI/CD test suites to prevent un-migrated models or manual database drifts from entering production.
