## ১. আমরা কী বানিয়েছি? (What did we build?)

আজকের সেশনে আমরা এমন একটি ব্যাকগ্রাউন্ড জব সিস্টেম তৈরি করেছি যা এপিআই রেসপন্স লেটেন্সিকে সর্বনিম্নে নামিয়ে আনে এবং একই সাথে সার্ভারকে মেমোরি লিক থেকে রক্ষা করে:
1. **পোস্ট-রেসপন্স এক্সিকিউশন (`BackgroundTasks`)**: ইউজার রেজিস্ট্রেশন বা প্রোফাইল আপডেটের সময় ওয়েলকাম ইমেইল পাঠানো এবং অডিট লগ রেকর্ডিংয়ের মতো পেরিফেরাল কাজগুলোকে মূল রিকোয়েস্ট-রেসপন্স সাইকেল থেকে আলাদা করে রেসপন্স পাঠানোর **পরে** এক্সিকিউট করা।
2. **ডিপেনডেন্সি লাইফটাইম ট্র্যাপ প্রতিরোধ (Safe Memory Boundaries)**: ব্যাকগ্রাউন্ড টাস্কের সিগনেচারে কোনো রিকোয়েস্ট-স্কোপড অবজেক্ট (যেমন ডাটাবেজ সেশন বা রিকোয়েস্ট অবজেক্ট) পাস না করে কেবল অপরিবর্তনশীল প্রিমিটিভ ডেটাটাইপ (`user_id: int`, `email: str`, `username: str`) পাস করার কড়া নিয়ম প্রতিষ্ঠা।
3. **ওওএম (OOM) মুক্ত বাউন্ডেড ইন-মেমোরি কিউ (`collections.deque(maxlen=1000)`)**: অডিট লগ সংরক্ষণের জন্য ফিক্সড-ক্যাপাসিটি সার্কুলার বাফার ব্যবহার করে মেমোরি ধারণক্ষমতাকে কঠোরভাবে $\mathcal{O}(1)$ কনস্ট্যান্ট স্পেসে সীমাবদ্ধ করা।
4. **ডিফেন্সিভ এক্সেপশন শিল্ড**: ব্যাকগ্রাউন্ড টাস্কের ভেতর আলাদা `try...except` ও স্ট্রাকচার্ড লগার স্থাপন, যাতে ইমেইল সার্ভার ডাউন হলেও এএসজিআই (ASGI) প্রসেস বা ইভেন্ট লুপ কোনোভাবেই ক্র্যাশ না করে।

## ২. বাস্তব জীবনের গল্প ও উপমা (Real-World Analogy)

### রেস্তোরাঁয় বিল পরিশোধ ও গ্রাহক বিদায় বনাম টেবিল পরিচ্ছন্নতা

কল্পনা করুন আপনি একটি অভিজাত রেস্তোরাঁয় ডিনার শেষ করেছেন:

#### ভুল ব্লকিং পদ্ধতি (Synchronous Post-Processing):
- আপনি ওয়েটারকে ক্রেডিট কার্ড দিয়ে বললেন, *"বিলটি নিন, আমি এখন যাব।"*
- ওয়েটার আপনার বিল প্রসেস করল, কার্ড সোয়াইপ করল। কিন্তু রসিদ আপনার হাতে না দিয়ে সে বলল, *"স্যার, এক মিনিট বসুন! আপনি তো খেয়ে চলে যাবেন, কিন্তু এই টেবিলের প্লেটগুলো আমাকে রান্নাঘরে গিয়ে ধুতে হবে, টেবিল মুছতে হবে এবং রেজিস্টার খাতায় কলম দিয়ে এন্ট্রি করতে হবে। আমি এগুলো শেষ করে এসে আপনাকে রসিদ দেব!"*
- আপনি টেবিল ছেড়ে উঠতে পারছেন না, দরজায় অন্য কাস্টমার ঢুকতে পারছে না। আপনার সময় নষ্ট হচ্ছে অহেতুক কারণে!

#### ব্যাকগ্রাউন্ড টাস্কের চমৎকার পদ্ধতি (Post-Response Execution):
- বুদ্ধিমান ওয়েটার আপনার কার্ড সোয়াইপ করে মিষ্টি হেসে রসিদটি আপনার হাতে তুলে দিয়ে বলল, *"ধন্যবাদ স্যার, আপনার ভ্রমণ শুভ হোক!"* (`HTTP 201 Created sent to client`)।
- আপনি নিশ্চিন্তে রেস্তোরাঁ থেকে বেরিয়ে গেলেন (লেটেন্সি মাত্র ৩৫ মিলিসেকেন্ড)।
- আপনি চলে যাওয়ার **পরে**, ওয়েটার ধীরেসুস্থে টেবিল পরিষ্কার করল, থালাবাসন কিচেনে পাঠাল এবং খাতায় অডিট এন্ট্রি করল (`BackgroundTasks executed post-response`)।

গ্রাহকের কাছে গুরুত্বপূর্ণ হলো সে তার কনফার্মেশন ও রসিদ তাৎক্ষণিক পেয়েছে কিনা; পেছনে থালাবাসন কখন ধোয়া হলো তা নিয়ে গ্রাহককে বসিয়ে রাখার কোনো যৌক্তিকতা নেই।

## ৩. এটা না বানালে কী মহাবিপদ হতো? (The Production Disaster Without It)

### বিপর্যয় ১: The Dependency Lifetime Trap (ক্লোজড সেশন ক্র্যাশ)
এটি ফাস্টএপিআই-এর সবচেয়ে কুখ্যাত ইন্টারভিউ ট্র্যাপগুলোর একটি:
```python
# ভয়াবহ ভুল কোড
@router.post("/users")
async def create_user(
    payload: UserCreate,
    bg: BackgroundTasks,
    db: AsyncSession = Depends(get_db_session),
):
    user = await service.create(payload)
    # মারাত্মক ভুল: রিকোয়েস্ট-স্কোপড db সেশন ব্যাকগ্রাউন্ডে পাস করা হয়েছে!
    bg.add_task(send_email_and_update_db, db, user.id)
    return user
```
**কেন এটি মহাবিপর্যয়?**  
FastAPI-এর `get_db_session` ডিপেনডেন্সির ভেতর একটি `yield` থাকে। যখনই রাউটার ফাংশনটি `return user` করে রেসপন্স পাঠায়, FastAPI তাৎক্ষণিকভাবে ডিপেনডেন্সির `finally:` ব্লক এক্সিকিউট করে এবং ডাটাবেজ সেশনটি **ক্লোজ (`session.close()`)** করে দেয়!  
এরপর যখন ব্যাকগ্রাউন্ড টাস্কটি চলতে যায়, সে দেখতে পায় ডাটাবেজ কানেকশন ইতোমধ্যে মৃত! সাথে সাথে প্রোডাকশন লগ ভরে ওঠে:  
`sqlalchemy.exc.InterfaceError: connection is closed` অথবা `MissingGreenlet: greenlet_spawn has not been spawned`।

### বিপর্যয় ২: আনবাউন্ডেড লিস্টের মেমোরি লিক ও ওওএম (Out-Of-Memory) ক্র্যাশ
যদি কেউ সাধারণ পাইথন লিস্টে অডিট লগ জমায়:
```python
AUDIT_LOGS = []  # সাধারণ পাইথন লিস্ট
```
সার্ভার চালু থাকার ৩ দিন পর যখন ১০ লাখ রিকোয়েস্ট আসবে, তখন এই লিস্টের সাইজ হবে গিগাবাইট সমান! ক্লাউড সার্ভারের র‍্যাম শেষ হয়ে ওএস কার্নেল সাথে সাথে `OOM-Killer (Out of Memory)` চালিয়ে পুরো ব্যাকএন্ড প্রসেস মেরে ফেলবে।

## ৪. আমাদের প্রজেক্টের আসল কোড ও কোডের সহজ ব্যাখ্যা (Real Code & Detailed Line-by-Line Breakdown in Bengali)

আসুন আমাদের প্রোডাকশন কোডবেস `app/services/notification_service.py` এবং `app/routers/user_router.py` থেকে সরাসরি কোড দেখে নেওয়া যাক:

### ক. বাউন্ডেড ইন-মেমোরি কিউ ও টাস্ক ফাংশন (`app/services/notification_service.py`)

```python
# মেমোরি সীমাবদ্ধ করার ধ্রুবক
MAX_AUDIT_ENTRIES: int = 1000
MAX_NOTIFICATION_ENTRIES: int = 1000

@dataclass(frozen=True)
class AuditLogEntry:
    """অপরিবর্তনশীল অডিট লগ রিপ্রেজেন্টেশন।"""
    action: str
    user_id: int
    timestamp: datetime

# লাইন ৪৬: ফিক্সড ক্যাপাসিটির সার্কুলার ডাবল-এন্ডেড কিউ
_AUDIT_LOG_STORE: deque[AuditLogEntry] = deque(maxlen=MAX_AUDIT_ENTRIES)
_NOTIFICATION_DISPATCH_STORE: deque[NotificationDispatchEntry] = deque(
    maxlen=MAX_NOTIFICATION_ENTRIES
)

async def send_welcome_notification(email: str, username: str) -> None:
    """সিগনেচারে শুধুই প্রিমিটিভ টাইপ (email: str, username: str) গ্রহণ করা হয়েছে।"""
    try:
        # বাহ্যিক নোটিফিকেশন নেটওয়ার্ক ল্যাটেন্সি সিমুলেশন (৫০ms)
        await asyncio.sleep(0.05)
        entry = NotificationDispatchEntry(
            email=email,
            username=username,
            timestamp=datetime.now(timezone.utc),
            status="dispatched",
        )
        _NOTIFICATION_DISPATCH_STORE.append(entry)
        logger.info("Successfully dispatched welcome notification to %s", email)
    except Exception as exc:
        # ডিফেন্সিভ শিল্ড: ব্যাকগ্রাউন্ডের এরর যেন মূল সার্ভারকে কখনো ডাউন না করে
        logger.error("Failed to dispatch notification to %s: %s", email, exc, exc_info=True)
```

### খ. রাউটার লেয়ারে টাস্ক যুক্ত করা (`app/routers/user_router.py`)

```python
@router.post(
    "/",
    response_model=UserResponse,
    status_code=status.HTTP_201_CREATED,
    summary="Register a new user",
)
async def create_user(
    payload: UserCreate,
    service: Annotated[UserService, Depends(get_user_service)],
    tx: Annotated[ScopedTransactionContext, Depends(get_transaction_context)],
    background_tasks: BackgroundTasks,  # FastAPI-র ব্যাকগ্রাউন্ড টাস্ক বাফার
) -> UserResponse:
    tx.stage("POST /users/")
    created_user = await service.create_user(payload=payload)

    # লাইন ১০৪-১১৪: শুধুমাত্র ইমিউটেবল প্রিমিটিভ আর্গুমেন্ট পাস করা হচ্ছে!
    background_tasks.add_task(
        send_welcome_notification,
        created_user.email,
        created_user.username,
    )
    background_tasks.add_task(
        record_audit_log,
        "create_user",
        created_user.id,
        datetime.now(timezone.utc),
    )

    return UserResponse.model_validate(created_user)
```

### কোডের লাইন-বাই-লাইন সহজ ব্যাখ্যা:
- **`deque(maxlen=1000)`**: পাইথনের C-লেভেলে অপ্টিমাইজড ডেটা স্ট্রাকচার। যখনই এতে ১০০০টি এন্ট্রি পূর্ণ হবে, পরবর্তী নতুন এন্ট্রি ঢুকলে এটি স্বয়ংক্রিয়ভাবে বাম পাশ থেকে সবচেয়ে পুরোনো এন্ট্রিটিকে মুছে ফেলে (`FIFO automatic eviction`)। কোনো ম্যানুয়াল স্ল্যাইসিং বা মেমোরি ম্যানেজমেন্টের দরকার হয় না।
- **`background_tasks.add_task(func, *args)`**: এটি কোনো কাজকে তখনই এক্সিকিউট করে না; এটি কেবল ফাংশন পয়েন্টার ও তার প্রিমিটিভ আর্গুমেন্টগুলোকে একটি অভ্যন্তরীণ পাইপলাইনে জমিয়ে রাখে।
- **প্রিমিটিভ টাইপ পাসিং**: লক্ষ্য করুন, আমরা কোনো `UserEntity` অবজেক্ট বা ডাটাবেজ সেশন পাস করিনি; আমরা পাস করেছি `created_user.email` (string) এবং `created_user.id` (int)। এর ফলে ব্যাকগ্রাউন্ড টাস্কটি রিকোয়েস্ট কনটেক্সট থেকে সম্পূর্ণ স্বাধীন হয়ে যায়।

## ৫. ডিএসএ (DSA) সহজ ভাষায় বিশ্লেষণ (DSA Complexity Made Simple)

| মেকানিজম / ডেটা স্ট্রাকচার | টাইম কমপ্লেক্সিটি | স্পেস কমপ্লেক্সিটি | গ্যারান্টি |
| :--- | :--- | :--- | :--- |
| **`deque.append()`** | $\mathcal{O}(1)$ | $\mathcal{O}(1)$ | মেমোরিতে ডাবল-লিঙ্কড নোড অ্যাপেন্ড কনস্ট্যান্ট টাইমে সম্পন্ন হয়। |
| **`deque(maxlen=K)` এভিকশন** | $\mathcal{O}(1)$ | $\mathcal{O}(K)$ বাউন্ডেড | বাফার ফুল হলে প্রাচীন ডেটা ডিসকার্ড হয় ইনস্ট্যান্টলি; মেমোরি কখনো $K=1000$-এর বেশি বাড়ে না। |
| **রেসপন্স ল্যাটেন্সি** | $\mathcal{O}(1)$ | — | বাহ্যিক নোটিফিকেশনের ৫০ms অপেক্ষা ক্লায়েন্টকে সহ্য করতে হয় না; রেসপন্স ডেলিভারি হয় **৩৫ মিলিসেকেন্ডের নিচে**। |

## ৭. এই দিনের RCA ও বাস্তব ভুল থেকে শিক্ষা (RCA Incident, Root Cause & Prevention)

### ইনসিডেন্ট: ব্যাকগ্রাউন্ড টাস্কে এক্সেপশন আনহ্যান্ডেল্ড থাকা

#### ক্ষতিকর প্যাটার্ন:
```python
async def bad_worker_task(email: str):
    # কোনো try-except নেই!
    res = await send_smtp_email(email)  # নেটওয়ার্ক ড্রপ হলে এক্সেপশন রেইজ হলো
```

#### রুট কজ (Root Cause):
যেহেতু ক্লায়েন্টের কাছে রেসপন্স ইতোমধ্যে পৌঁছে গেছে, তাই ব্যাকগ্রাউন্ড টাস্কের ভেতর কোনো আনহ্যান্ডেল্ড এরর ঘটলে ক্লায়েন্ট তা জানতে পারে না; বরং সেই এক্সেপশনটি পাইথন ইভেন্ট লুপে বাবল আপ করে ইউভিকর্ন (Uvicorn) কনসোলকে দূষিত করে এবং কোনো কোনো ক্ষেত্রে ফ্রেমওয়ার্কের ভেতরে সাইলেন্টলি হারিয়ে যায়।

#### সমাধান:
প্রতিটি ব্যাকগ্রাউন্ড ওয়ার্কার টাস্কের ভেতর বাধ্যতামূলকভাবে `try...except Exception as exc:` ব্লক থাকতে হবে এবং এররটিকে স্ট্রাকচার্ড লগে `logger.error(..., exc_info=True)` দিয়ে সেন্ট্রি বা লগ সার্ভারে পাঠাতে হবে।

## ৮. ইন্টারভিউ ও ভাইভা প্রশ্ন (Interview Questions & Model Answers)

### প্রশ্ন ১: FastAPI-র ইন-প্রসেস `BackgroundTasks` এবং Celery/RabbitMQ/Redis Queue-এর মধ্যে পার্থক্য কী এবং কখন কোনটি ব্যবহার করবেন?
**উত্তর**:  
- **FastAPI `BackgroundTasks`**: এটি একই পাইথন প্রসেসের ভেতর ইভেন্ট লুপের সাহায্যে চলে। এটি অত্যন্ত লাইটওয়েট, কোনো অতিরিক্ত ইনফ্রাস্ট্রাকচার (Redis/RabbitMQ) লাগে না।  
  *ব্যবহার*: দ্রুত এবং অপশনাল কাজের জন্য, যেমন রিকোয়েস্টের পর হালকা অডিট লগ লেখা বা একটি সাধারণ ওয়েলকাম ইমেইল পাঠানো। যদি সার্ভার রিস্টার্ট হয় বা ক্র্যাশ করে, তবে কিউতে থাকা কাজগুলো মুছে যাবে।
- **Celery / BullMQ / RQ**: এগুলো হলো ডেডিকেটেড ডিসট্রিবিউটেড টাস্ক কিউ। কাজগুলো ডাটাবেজ বা ব্রোকারে (Redis) পারসিস্ট থাকে।  
  *ব্যবহার*: মিশন-ক্রিটিক্যাল কাজের জন্য, যেমন পেমেন্ট প্রসেসিং, ভারী ভিডিও এনকোডিং, পিডিএফ রিপোর্ট জেনারেশন, অথবা কোনো কাজ ফেইল করলে স্বয়ংক্রিয় রিট্রাই (Retry policy) লাগলে।

### প্রশ্ন ২: ব্যাকগ্রাউন্ড টাস্কে যদি ডাটাবেজে রাইট করার প্রয়োজন হয়, তবে কীভাবে নিরাপদভাবে করতে হয়?
**উত্তর**:  
রিকোয়েস্ট হ্যান্ডলারের ডিবির সেশন পাস করা যাবে না। ব্যাকগ্রাউন্ড টাস্ক ফাংশনটির ভেতরে স্বাধীনভাবে `async_session_factory()` কল করে একটি সম্পূর্ণ নতুন ডাটাবেজ সেশন তৈরি করতে হবে:
```python
async def background_db_worker(user_id: int):
    async with async_session_factory() as session:
        # সম্পূর্ণ নতুন সেশন যা ব্যাকগ্রাউন্ড টাস্ক শেষ হলে নিজে ক্লোজ হবে
        await session.execute(...)
        await session.commit()
```

## ৯. এক নজরে আসল মূল লজিক (The Core Bottom-Line Logic)

> **গোল্ডেন রুলস**:
> 1. ক্লায়েন্টকে আটকে রাখবেন না; পেরিফেরাল কাজগুলোকে `background_tasks.add_task` দিয়ে রেসপন্সের পরে চালান।
> 2. ব্যাকগ্রাউন্ড টাস্কে কখনো রিকোয়েস্ট-স্কোপড অবজেক্ট (DB Session, Request) পাঠাবেন না; শুধুই ইমিউটেবল প্রিমিটিভ (int, str, float) পাস করুন।
> 3. ইন-মেমোরি স্টোরেজের জন্য কখনো আনবাউন্ডেড লিস্ট ব্যবহার করবেন না; সর্বদা `collections.deque(maxlen=K)` দিয়ে মেমোরিকে নির্দিষ্ট বাউন্ডারিতে বেঁধে রাখুন।
