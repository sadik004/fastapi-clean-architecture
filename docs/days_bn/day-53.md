# Day 53: ARQ সহযোগে অ্যাসিঙ্ক্রোনাস টাস্ক কিউ ও কো-রুটিন ওয়ার্কার (Asyncio-Native Task Queues with ARQ & Coroutine Workers)

---

### ১. আমরা কী বানিয়েছি? (What did we build?)

আমরা পাইথনের **নেটিভ `asyncio` ইভেন্ট লুপ** এবং **রেডিস ব্যাকএন্ড**-এর উপর ভিত্তি করে একটি আল্ট্রা-লাইটওয়েট ব্যাকগ্রাউন্ড টাস্ক কিউ আর্কিটেকচার তৈরি করেছি, যার নাম **ARQ (Async Redis Queue)**।

প্রথাগত Celery ওয়ার্কারগুলো ওএস-লেভেল প্রি-ফোর্ক প্রসেস পুল (Multiprocessing) ব্যবহার করে, যেখানে প্রতিটি ওয়ার্কার প্রসেস ৬০–৮০ মেগাবাইট র্যাম দখল করে বসে থাকে। কিন্তু যেসব কাজ মূলত নেটওয়ার্ক বা আই/ও-বাউন্ড (যেমন: বাইরের পেমেন্ট গেটওয়েতে ওয়েবহুক পাঠানো, মোবাইল অ্যাপে পুশ নোটিফিকেশন ব্রডকাস্ট করা, কিংবা থার্ড-পার্টি এপিআই সিঙ্ক করা)—সেগুলোর জন্য ভারী সিপিইউ প্রসেস চালু করা এক বিরাট অপচয়।

আমরা ARQ-এর সাহায্যে একটি একক লাইটওয়েট প্রসেসে (<৩০ মেগাবাইট র্যাম) শত শত কনকারেন্ট কো-রুটিন (`async def`) একযোগে নন-ব্লকিংভাবে চালানোর ব্যাকগ্রাউন্ড সিস্টেম এবং ফাস্টএপিআই ম্যানেজমেন্ট এপিআই তৈরি করেছি।

### ২. 📌 ব্যবহৃত DSA ও আর্কিটেকচারাল প্যাটার্নের নাম

* **আর্কিটেকচারাল প্যাটার্ন**: **নেটিভ অ্যাসিঙ্ক্রোনাস টাস্ক কিউ ও সিঙ্গেল-প্রসেস কো-রুটিন পুল (Asyncio-Native Task Queue — ARQ with Non-Blocking Coroutine Workers & Shared Client Pool)**
* **ডিএসএ ও কনকারেন্সি মেকানিক্স**:
  * **অ্যাসিঙ্ক্রোনাস ইভেন্ট লুপ মাল্টিপ্লেক্সিং (Asyncio Event Loop Task Multiplexing)** — একক ওএস থ্রেডে হাজার হাজার সকেট আই/ও নন-ব্লকিং হ্যান্ডলিং।
  * **রেডিস লিস্ট/জেডসেট জব এনকিউ ও ডিকিউ ($\mathcal{O}(1)$ Push/Pop)** — সাব-মিলিসেকেন্ড ডিসপ্যাচ লেটেন্সি।
  * **কানেকশন পুল রিউজ (Shared Persistent Connection Pool)** — সকেট অ্যালগ্রিথমিক ওভারহেড সম্পূর্ণ নির্মূল।

### ৩. 🚀 প্রোডাকশনে ঠিক কখন ব্যবহার করব? (When to use in Production)

1. **আউটবাউন্ড ওয়েবহুক ও এপিআই নোটিফিকেশন ডেলিভারি (Outbound Webhooks)**:
   * কাস্টমার বা পার্টনার সার্ভারে অর্ডার কমপ্লিশন বা পেমেন্ট কনফার্মেশন ওয়েবহুক পাঠাতে।
2. **পুশ নোটিফিকেশন ও মেসেজ ব্রডকাস্ট (High-Throughput Notification Fan-Out)**:
   * ১০,০০০ ইউজারের ফোনে একসাথে পুশ নোটিফিকেশন পাঠাতে, যেখানে কাজটা মূলত নেটওয়ার্ক আই/ও-বাউন্ড।
3. **মেমোরি-সংবেদনশীল ক্লাউড কন্টেইনার (Memory-Constrained Cloud Deployments)**:
   * যেখানে এডব্লিউএস বা ডিজিটাল ওশানের সার্ভার মেমোরি ২৫৬ বা ৫১২ মেগাবাইট, সেখানে সেলারির বদলে ARQ ব্যবহার করে মেমোরি খরচ ৯০% কমিয়ে আনা।
4. **নেটিভ `async/await` ব্যাকগ্রাউন্ড জবস**:
   * যেখানে কোডবেসের সমস্ত ডেটাবেস এবং এইচটিটিপি ক্লায়েন্ট অলরেডি `asyncio`-তে লেখা (`httpx.AsyncClient`)।

### ৪. 🎯 কী কারণে বা কোন পরিস্থিতিতে ব্যবহার করব? (Why to use / Technical Triggers)

* **র্যাম মেমোরি ওভারহেড ৯০% কমানো**: সেলারিতে ১০টি কনকারেন্ট কাজের জন্য ১০টি ওএস প্রসেসে ৮০০ মেগাবাইট র্যাম দরকার হয়। ARQ-তে একক প্রসেসে মাত্র ২৫ মেগাবাইট র্যাম দিয়ে ১০০টি কনকারেন্ট কো-রুটিন অনায়াসে চলে।
* **জিরো ইভেন্ট লুপ কনফ্লিক্ট (Native Coroutines)**: কোনো থ্রেডপুল কনভার্সন বা সিঙ্ক্রোনাস ব্লকিং ছাড়াই খাঁটি `async def` কোড চলে।
* **সাব-মিলিসেকেন্ড ডিসপ্যাচ লেটেন্সি**: সরাসরি রেডিসে জবের মেটাডাটা পুশ করে ফাস্টএপিআই ক্লায়েন্টকে <১ms-এ **HTTP 202 Accepted** ফেরত দেয়।

### ৫. বাস্তব জীবনের গল্প ও উপমা: বিশাল ১০ চাকার মালবাহী ট্রাক (Celery) বনাম আল্ট্রাফাস্ট ইলেকট্রিক ড্রোন (ARQ)-এর উপমা

কল্পনা করুন, একটি কুরিয়ার সার্ভিস কোম্পানিতে ডেলিভারির কাজ হয়।

* **Celery হলো বিশাল ১০ চাকার হেভি-ডিউটি মালবাহী ট্রাক**:
  * আপনি যদি একটি বড় স্টিলের আলমারি বা কংক্রিটের স্ল্যাব (ভারী CPU টাস্ক, যেমন ৫০ পৃষ্ঠার পিডিএফ রেন্ডারিং বা ভিডিও কনভার্সন) এক শহর থেকে অন্য শহরে পাঠাতে চান, তবে এই ট্রাকের বিকল্প নেই। তবে সমস্যা হলো—ট্রাক চালাতে প্রচুর তেল (RAM মেমোরি) পোড়ে এবং ইঞ্জিন চালু হতে সময় লাগে।
* **ARQ হলো আল্ট্রাফাস্ট ব্যাটারিচালিত ইলেকট্রিক ড্রোন**:
  * যদি আপনাকে কেবল একটি কাগজের চিঠি বা ছোট প্যাকেট (লাইটওয়েট I/O টাস্ক, যেমন একটি ওয়েবহুক কল বা এসএমএস অ্যালার্ট) পাঠাতে হয়, তবে সেই ১০ চাকার ট্রাক স্টার্ট করা চরম বোকামি! ড্রোনটি কোনো তেল না পুড়িয়ে মুহূর্তেই বাতাসে উড়ে গিয়ে চিঠি ডেলিভারি দিয়ে চলে আসে।

আমাদের ব্যাকএন্ডে **Celery** থাকবে ভারী কাজের জন্য, আর **ARQ** থাকবে দ্রুতগতির আই/ও নেটওয়ার্ক কাজের জন্য!

### ৬. এটা না বানালে কী মহাবিপদ হতো? (The Production Disaster Without It)

যদি আমরা প্রতিটি সাধারণ এপিআই কল বা নোটিফিকেশনের জন্য সেলারির মতো প্রসেস-বেসড ওয়ার্কার চালাতাম:

```
[Celery Worker 1: 75 MB] ──┐
[Celery Worker 2: 75 MB] ──┼──> মোট র্যাম খরচ = 750 MB!
[Celery Worker 10: 75 MB] ─┘   (AWS 512MB RAM কন্টেইনার মুহূর্তেই OOM Kill হয়ে ক্র্যাশ করত!)
```

1. **আউট অফ মেমোরি (OOM Crash)**: ছোট কন্টেইনারে মেমোরি শেষ হয়ে পুরো সার্ভার রিবুট নিত।
2. **সকেট এগজশন (Socket Churn)**: প্রতিটা টাস্কে নতুন এইচটিটিপি ক্লায়েন্ট তৈরি করে কানেকশন হ্যান্ডশেকে বিপুল ল্যাটেন্সি তৈরি হতো।

### ৭. আমাদের প্রজেক্টের আসল কোড ও লাইনের সহজ ব্যাখ্যা (Real Code & Detailed Line-by-Line Breakdown)

#### (১) ARQ ওয়ার্কার সেটিংস ও লাইফস্প্যান হুক (`app/core/arq_app.py`)

```python
async def startup(ctx: dict[str, Any]) -> None:
    # ওয়ার্কার চালু হওয়ার সময় একবার একটি শেয়ার্ড এইচটিটিপি ক্লায়েন্ট তৈরি হয়
    ctx["http_client"] = httpx.AsyncClient(timeout=10.0)

async def shutdown(ctx: dict[str, Any]) -> None:
    # ওয়ার্কার বন্ধের সময় নিরাপদভাবে নেটওয়ার্ক সকেট ড্রেন ও ক্লোজ করা হয়
    client: httpx.AsyncClient | None = ctx.get("http_client")
    if client is not None:
        await client.aclose()

class WorkerSettings:
    functions = [sync_webhook_notification, broadcast_push_notification]
    redis_settings = get_arq_redis_settings()
    max_jobs = 100        # একটি একক প্রসেসেই ১০০টি কনকারেন্ট টাস্ক
    job_timeout = 60      # ৬০ সেকেন্ড টাইমআউট
    keep_result = 3600    # ১ ঘণ্টা ফলাফল সংরক্ষণ
    on_startup = startup
    on_shutdown = shutdown
```

* **`ctx["http_client"]`**: প্রতিটি জবের ভেতর বারবার নতুন ক্লায়েন্ট না বানিয়ে সেন্ট্রাল পুল থেকে শেয়ার করা হয়।

#### (২) নেটিভ অ্যাসিঙ্ক টাস্ক কো-রুটিন (`app/tasks/arq_tasks.py`)

```python
async def sync_webhook_notification(
    ctx: dict[str, Any],
    webhook_url: str,
    payload: dict[str, Any],
) -> dict[str, Any]:
    """নন-ব্লকিংভাবে বাইরের এপিআই-তে ওয়েবহুক পাঠায়।"""
    timestamp = datetime.now(UTC).isoformat()
    client: httpx.AsyncClient | None = ctx.get("http_client")

    status_code = 200
    if client is not None:
        response = await client.post(webhook_url, json=payload)
        status_code = response.status_code

    return {
        "status": "DELIVERED",
        "webhook_url": webhook_url,
        "status_code": status_code,
        "attempted_at": timestamp,
    }
```

* ফাংশনটি ১০০% `async def`, কোনো থ্রেডপুল ছাড়াই পিওর ইভেন্ট লুপে চলে।

#### (৩) সার্ভিস ও এপিআই এন্ডপয়েন্ট (`app/services/arq_service.py` & `app/routers/arq_router.py`)

```python
@router.post("/jobs/webhook", status_code=status.HTTP_202_ACCEPTED)
async def enqueue_webhook_job(request: WebhookJobRequest) -> ArqJobEnqueueResponse:
    job_id = await ArqService.enqueue_webhook_task(
        webhook_url=request.webhook_url,
        payload=request.payload,
    )
    return ArqJobEnqueueResponse(
        job_id=job_id,
        job_name="sync_webhook_notification",
        status="QUEUED",
        message="Outbound webhook job enqueued successfully.",
    )
```

* ক্লায়েন্ট রিকোয়েস্ট পাঠানোর সাথে সাথে মিলি-সেকেন্ডে `HTTP 202 Accepted` এবং ট্র্যাকিংয়ের জন্য `job_id` পেয়ে যায়।

### ৮. ডিএসএ ও এআরকিউ মেকানিক্স (Asyncio Event Loop Concurrency & Redis Storage)

1. **ইভেন্ট লুপ মাল্টিপ্লেক্সিং (Non-Blocking Multiplexing)**:
   * ওএস থ্রেডের কনটেক্সট সুইচের পরিবর্তে পাইথনের কো-রুটিন যখন `await client.post()` করে, তখন সিপিইউ অলস বসে না থেকে কিউ থেকে অন্য ইউজারের ওয়েবহুক কল শুরু করে দেয়।
2. **রেডিস কিউ ইনজেকশন ($\mathcal{O}(1)$ Push/Pop)**:
   * টাস্কের ইনপুট আর্গুমেন্টগুলো মেসেজপ্যাক বা বাইনারি ফরম্যাটে রেডিসের কিউতে পুশ হয়। ফলে মেমোরি ফুটপ্রিন্ট অত্যন্ত নগণ্য থাকে।

> "কাজের ধরনের ওপর ভিত্তি করে এই নির্বাচন করতে হয়:
> ১. **Celery**: যখন কাজগুলো **CPU-ইন্টেনসিভ বা সিঙ্ক্রোনাস** (যেমন: মেশিন লার্নিং ইনফারেন্স, ইমেজ রিসাইজিং, পিডিএফ/এক্সেল তৈরি বা ভারী ক্রিপ্টোগ্রাফি)। কারণ সেলারি ওএস প্রসেস পুলে চলে, যা পাইথনের গিল (GIL) বাইপাস করে মাল্টি-কোর ব্যবহার করতে পারে।
> ২. **ARQ**: যখন কাজগুলো **I/O-বাউন্ড বা নেটওয়ার্ক-ইন্টেনসিভ** (যেমন: ওয়েবহুক পুশ, নোটিফিকেশন ব্রডকাস্ট, বাইরের এপিআই কল বা ডেটাবেস বাল্ক ফেচ)। কারণ ARQ খাঁটি `asyncio` কো-রুটিনে চলে। সেলারির ১০টি ওয়ার্কার চালাতে যেখানে ১ জিবি র্যাম লাগে, ARQ-তে একক প্রসেসে মাত্র ২৫ মেগাবাইট র্যামে ১০০টি কনকারেন্ট নেটওয়ার্ক কল পরিচালনা করা যায়।"

#### প্রশ্ন ২: ARQ ওয়ার্কারের `ctx` ডিকশনারি কেন এত গুরুত্বপূর্ণ?
**আদর্শ উত্তর**:
> "`ctx` (Context) হলো ARQ-এর একটি প্রসেস-লেভেল স্টেট ডিকশনারি। `startup` লাইফস্প্যানে এর ভেতরে `httpx.AsyncClient` বা ডেটাবেস কানেকশন পুল ইনিশিয়ালাইজ করে রাখা যায়। এর ফলে প্রতিবার টাস্ক এক্সিকিউশনের সময় নতুন এইচটিটিপি সেশন খোলার টিসিপি/টিএলএস ওভারহেড থাকে না, বরং বিদ্যমান কানেকশন পুলটি রিইউজ হয়ে নেটওয়ার্ক ল্যাটেন্সি নূন্যতম থাকে।"

---

### ১০. এক নজরে আসল মূল লজিক (The Junior Architect's Operational Checklist)

1. **I/O vs CPU Segregation**: I/O-বাউন্ড কাজের জন্য **ARQ** ব্যবহার করব, আর ভারী CPU-বাউন্ড কাজের জন্য **Celery** ব্যবহার করব।
2. **Context Pool Invariant**: কখনোই টাস্কের ভেতরে `async with httpx.AsyncClient():` লিখব না; সর্বদা `ctx['http_client']` ব্যবহার করব।
3. **HTTP 202 Contract**: ব্যাকগ্রাউন্ডে কিউ করার এন্ডপয়েন্টগুলো সর্বদা **`202 Accepted`** ও ট্র্যাকিং `job_id` ফেরত দেবে।
